## BILL-4 Checkpoint C — edges: proration, tax, skip/exclude/void, gaplessness, IDOR (2026-07-26, `docs/api-contracts/BILL-4-SPEC.md`) — the last checkpoint of BILL-4

**Rulings applied from Srijan's Checkpoint B review, each now locked in:**
- **Sequence reset-policy**: built for real this checkpoint (`FinanceSettingsService`/`FinanceSettingsController`, `GET`+`PATCH /finance/settings`, backed by a new `tenants.invoiceNumberingReset` boolean added via a real Prisma migration). `bill-post.util.ts`'s `buildInvoiceSequenceKey` now takes the flag + a real `fiscalYearBs(bsYear, bsMonth)` (Shrawan/month-4-based) instead of Checkpoint B's CONTINUOUS-only stub.
- **FAILED lines not auto-retried**: confirmed intentional, not a shortfall — promoted from a BILL-BUGS note to a real locked ruling, **B4-11**, added directly to `BILL-4-SPEC.md` §1.
- **TRANSPORT-ITEM**: investigated, **not fixed this checkpoint**. `bill_invoice_items.fee_head_id` is `NOT NULL` with no `transport_route_id` column — cleanly fixing it needs a real migration (nullable `fee_head_id` + a new nullable `transport_route_id` + a CHECK ensuring exactly one is set) plus resolver/runner changes to itemize transport. Given the explicit instruction not to force it if it risks this checkpoint's scope, and given the checkpoint's own required deliverables (proration, tax, skip/exclude/void, gaplessness, IDOR, read endpoints, the full whole-class proof) already filled the available runway, this stays exactly as flagged at Checkpoint B: transport's amount is still correctly included in every total, only the itemized breakdown omits it. Left open for a small follow-on before BILL-8.
- **FIX-DUE-DAYS**: no change — already logged as its own backlog item at Checkpoint B, not folded in here.

**Architecture — `BillLineResolverService`** (new, shared by both `BillRunService`'s draft generation and `BillRunPostRunnerService`'s posting, so what the accountant previews is exactly what gets posted): replaces Checkpoints A/B's `asOfDate = day 1 of the target BS month` with a genuine **period-overlap** assignment lookup (`StudentFeeStructureAssignmentService.findAssignmentOverlappingPeriod`, new) spanning `[periodStart, periodEnd]`, then uses `periodEnd` as `FeePreviewService`'s own `asOfDate` — day-1 would have silently missed (SKIPPED_NO_ASSIGNMENT'd) a student whose assignment starts mid-month, exactly the case B4-5 needs to prorate instead.

**Proration** (B4-5): per-fee-head, gated on `fee_heads.proration_policy = 'MONTHLY'`. Fraction = `(daysInMonth - dayOfMonth(effective_from) + 1) / daysInMonth`, applied identically to that head's gross and net (concession is derived as `gross - net` post-scaling, never scaled separately, so the three stay arithmetically consistent to the paisa). A `NONE`-policy head on the same invoice is never scaled, confirmed live and by unit test in the same run. **Two narrow, documented simplifications, not fully addressed**: whole-bill concessions (`fee_head_id IS NULL`) use `FeePreviewService`'s own computed dollar amount as-is, not re-derived against the prorated subtotal; transport is folded into totals unprorated (same TRANSPORT-ITEM gap). Neither was exercised together with proration in this checkpoint's live proof — each proven in isolation.

**Tax** (B4-9, R4): real `tax_rates` lookup (`effective_from <= periodEnd <= COALESCE(effective_to, periodEnd)`, at most one active row by the table's own pre-existing overlap constraint) computed on the post-proration, post-concession per-head net, eligibility gated by `applies_to` (`ALL` vs `TAXABLE_HEADS` + `fee_heads.is_taxable`). Snapshotted onto the invoice (`tax_rate`, `tax_amount`, `taxable_base`) and never recomputed after posting — live-proven by deactivating the rate immediately after posting and re-reading the identical invoice unchanged.

**A real, unplanned bug found live-proofing the reset-policy toggle — flagged, not silently patched:** the visible `invoice_number` format (`BINV-<bsYear>-<seq>`) embeds only *today's BS year*, never which sequence *key* produced the value. Toggling a tenant to RESET mode starts a brand-new `bill_invoice:<slug>:<fiscalYear>` key at value 1 — and if the tenant already has a CONTINUOUS-mode invoice numbered 1 in the *same* `bsYear` (exactly demo's state: Chameli's `BINV-2083-000001` from Checkpoint B), the very first RESET-mode post collides on `bill_invoices.invoice_number`'s UNIQUE constraint and every line in that run comes back FAILED. Live-reproduced exactly this way (4 students, all FAILED with an identical `23505` "invoice_number already exists" error) before reverting demo's setting back to `false`. **The per-student transaction correctly rolled back the sequence increment along with the failed insert** (confirmed: the fiscal-year-keyed sequence row was never created; each of the 4 attempts independently computed value 1 and collided identically) — so this is a pure invoice_number-format gap, not a deeper transactional integrity problem. **Raising, not deciding:** a real fix needs either a mode-disambiguating segment in the visible number format, or scoping `invoice_number` uniqueness per sequence-key rather than globally — tracked here as **FIX-RESET-COLLISION** for Srijan to prioritize. Until fixed, treat the reset-policy toggle as effectively a one-time, at-onboarding decision — do not flip it on a tenant with existing CONTINUOUS invoices in the current BS year. The four FAILED lines from this reproduction are left exactly as they landed (a run that completed with all-FAILED lines, matching B4-11's "surface for a human, don't retry" ruling) rather than manually forced into a fixed state.

**A second, smaller bug found and fixed in the same design pass** (`bill-run-post-runner.service.ts`): `postLine` re-derives the per-head breakdown via a fresh `BillLineResolverService.resolve()` call at post time, but had no check that this fresh call still returns `outcome: 'DRAFT'`. If something changes between draft and post (the exact scenario B4-6 assumes doesn't happen, but should still fail safely if it does — e.g. the assignment is deleted), the code would have crashed ungracefully instead of producing a clean FAILED line. Fixed with an explicit check; used live to engineer this checkpoint's own FAILED demonstration (Elina's assignment soft-deleted between draft and post) rather than an artificial fixture hack.

**Endpoints added**: `PATCH /finance/bill/runs/:id/exclude` (DRAFT lines only, re-aggregates totals), `DELETE /finance/bill/runs/:id` (void a DRAFT wholesale, soft-delete frees the idempotency key), `GET /finance/bill/invoices` (list, `ACCOUNTANT_AND_ABOVE` only — spec names no parent scoping for the bare list), `GET /finance/bill/invoices/:id` + `GET /finance/students/:studentId/bill/invoices` (both parent object-scoped via the established `assertGuardianOwnsStudent` pattern, reused verbatim — no new IDOR-check code invented).

## BILL-4 Checkpoint B — idempotent posting + the ledger invariant (2026-07-26, `docs/api-contracts/BILL-4-SPEC.md`)

**Architecture**: posting is a genuine background job, not a synchronous request wearing a job-shaped response — mirrors BILL-2's bulk-assign split. `BillRunService.requestPost` only flips `bill_runs.status` `DRAFT → POSTING` and stamps `posted_by` (idempotent: `POSTED`/`POSTING` are no-ops, `VOIDED` is rejected). `BillRunPostPoller` (`@Interval`, 10s, identical shape to `BulkAssignPoller` — no BullMQ) drains every tenant's `POSTING` runs via `BillRunPostRunnerService`, which re-selects `bill_run_lines WHERE outcome = 'DRAFT'` fresh on every pass — already-`POSTED` lines are never re-attempted, giving the resumability the spec asks for with no separate progress-counter columns needed.

**Extracted `LedgerService.postEntryInTx`** (+ made `withStudentLock` public) so the per-student advisory lock, the `bill_invoice`/`bill_invoice_items` insert, and the ledger entry insert all happen inside **one** transaction under **one** lock acquisition — mirrors the `recordPaymentInTx` extraction precedent (PAY-1) exactly: same reasoning, a different caller composing shared write logic into its own bigger transaction rather than nesting two independent top-level transactions (which would not share atomicity).

**R13's sequence-key infrastructure did not exist anywhere before this checkpoint** — grepped the whole codebase; only the OLD flat `invoice_seq`/`payment_seq` keys exist. This is the first real use of R13's namespaced shape. **Built CONTINUOUS-only**: the key is `bill_invoice:<tenantSlug>:CONTINUOUS` (`bill-post.util.ts`), not a real "tenant's inception year" lookup — no tenant setting for reset-per-fiscal-year exists (checked: no such column on `public.tenants`), and under CONTINUOUS the exact anchor value doesn't matter as long as it never changes, which a literal string trivially guarantees without a new cross-schema query. Full reset-policy support (and the setting that would toggle it) is Checkpoint C's numbering-gaplessness scope, not built here. The VISIBLE `invoice_number` (`BINV-<bsYear>-NNNNNN`) still labels the CURRENT bs year at post time, matching the old system's own convention — only the underlying counter key changed shape.

**`FAILED` lines are not auto-retried by a later post/drain.** A per-student failure marks that line `FAILED` and the run still completes (transitions to `POSTED` once every line has been attempted) — satisfies "does not abort the rest of the run." But "re-posting the run picks up only non-posted lines" is implemented literally as `WHERE outcome = 'DRAFT'` only, not `IN ('DRAFT','FAILED')`. Building an explicit retry-a-FAILED-line path is Checkpoint C's "failed-line tolerance" scope — flagging the narrower interpretation now rather than silently deciding it's the same thing.

**Transport has no `fee_head_id` and cannot become a `bill_invoice_item`** under the current schema (`bill_invoice_items.fee_head_id` is `NOT NULL`, and there's no `transport_route_id` column). A student with a transport assignment would still have its amount correctly folded into the invoice's aggregate totals (via `bill_run_lines.net`, computed by the unmodified `FeePreviewService`), but the itemized breakdown would silently omit a transport line. Not hit by this checkpoint's proof (Chameli has no transport assignment) — raising as a genuine, unresolved DDL gap rather than inventing a column unilaterally.

**Per-head `bill_invoice_items` are derived by re-calling `FeePreviewService.preview()` at post time**, using the same `asOfDate` formula the draft used (`bsToAd({bsYear, bsMonth, day:1})`) — `bill_run_lines` only ever stored the student's aggregate gross/concession/net, not a per-head breakdown, so there was nowhere else to get it from without a new migration. This assumes nothing changed between draft and post (B4-6's own assumption: catalog edits happen only at the draft stage, via regenerate). The read happens *before* the per-student lock is acquired, since it's read-only and doesn't need to participate in the locked transaction.

**FIX-DUE-DAYS (backlog item, not blocking BILL-4):** Checkpoint A's `DEFAULT_DUE_DAYS = 15` constant + per-run `dueDate` override stands as-is per Srijan's explicit call. Building a real tenant-configurable due-days setting (R8's literal "tenant-configurable") is deferred to its own future backlog item, tracked here as **FIX-DUE-DAYS**, not folded into BILL-4.

**Live proof (`demo` tenant, Chameli Tamang — chosen by Srijan for already carrying BILL-3's real ledger history).** Read-first correction before touching anything: Srijan's recollection was "she carries a real 5,000 opening balance" — true as one entry, but her **actual current balance is 5,500**, not 5,000, because two BILL-3 Checkpoint-4 concurrency-probe adjustments (+200, +300) permanently remain on her ledger alongside a goodwill-credit-and-reversal pair that nets to zero. Confirmed via both a raw `SELECT` and the live `GET /finance/students/:id/balance` endpoint before proceeding — the invariant below uses the real number, not the recalled one.

Created fresh fixtures (fee head "BILL-4 Checkpoint B Tuition", a Grade 9 `bill_fee_structure` with one 3,000 item, assigned to Chameli only) via the real HTTP endpoints. `POST /finance/bill/runs` (CLASS/Grade 9/academic year 2082-83/bsYear 2082/bsMonth 4) → `DRAFT:1, SKIPPED_NO_ASSIGNMENT:14`. `POST .../post` → `status: POSTING`, `postedBy` stamped immediately. Polled `GET .../runs/:id` against the **real, unmodified `@Interval` poller** (no manual trigger) — completed in under 6 seconds, `status: POSTED`.

Raw `SELECT`s: `bill_invoices` row — `invoice_number: BINV-2083-000001`, `gross_amount: 3000.00`, `previous_balance: 5500.00`, `net_amount: 3000.00`, `total_receivable: 8500.00`, `status: POSTED`, `ledger_entry_id` populated. The new ledger entry — **exactly one**, `entry_type: INVOICE`, `debit: 3000.00`, `credit: 0.00` (the invoice's own charge only — the previous balance was never re-posted). Balance after, both via raw `SELECT COALESCE(SUM(debit)-SUM(credit),0)` and the cached `student_account_balances` row and the live `GET /finance/students/:id/balance` endpoint: **8500.00** everywhere, consistently — matching `5500 + 3000` exactly, not `8000` (Srijan's spec-illustrative figure) and nowhere near `13000` (the double-count bug this whole invariant exists to catch). `bill_invoice_items`: one row, "BILL-4 Checkpoint B Tuition", `3000.00`/`3000.00`, `is_taxable: false`.

**Live-data discipline:** the run/invoice/ledger-entry/invoice-item rows created by this proof are now **permanent** — same structural note as BILL-3's Checkpoint 4 (no immutability trigger on `bill_invoices` itself, but a posted invoice is spec-immutable by design per B4-6, and its ledger entry genuinely can't be deleted). The fee-structure assignment and the `bill_fee_structures` row (+ its item) were fresh scaffolding, not part of the permanent record, and were deleted with read-backs. The fee head could **not** be hard-deleted — its own delete attempt hit a real FK violation (`bill_invoice_items.fee_head_id` still references it, correctly, since that item row is now permanent) — soft-deleted instead via the real `DELETE /finance/fee-heads/:id` endpoint, confirmed via `deleted_at` read-back. The owner password shim was restored and 401-proven.

**876 api tests passing (108 suites; +18 tests / +2 suites this checkpoint: 6 new tests in `bill-post.util.spec.ts`, 5 new tests in `bill-run-post-runner.service.spec.ts` — both new suites — plus 5 new `requestPost` tests in the existing `bill-run.service.spec.ts` and 2 new tests (`postEntryInTx`, `withStudentLock` visibility) in the existing `ledger.service.spec.ts`), `tsc -p tsconfig.build.json --noEmit` clean.**

## BILL-4 Checkpoint A — draft billing run engine (2026-07-26, `docs/api-contracts/BILL-4-SPEC.md`)

**Tables** (`0022_bill_run.sql`, canary demo → all 8 tenants): `bill_runs`, `bill_run_lines`, `bill_invoices`, `bill_invoice_items` — all four created now per spec §2's full DDL, even though this checkpoint's draft-generation code only ever writes `bill_runs`/`bill_run_lines` (posting is Checkpoint B). `bill_run_lines.bill_invoice_id → bill_invoices(id)` is added as a trailing `ALTER TABLE` (Postgres can't forward-reference a table that doesn't exist yet when the migration follows the spec's own table ordering).

**R8's tenant-configurable due-days setting doesn't exist as infrastructure anywhere in the codebase** — checked: no `due_days`/`dueDays` column on `public.tenants` or any settings table, and neither BILL-0/1/2/3 nor this spec's own DDL adds one. `CreateBillRunDto.dueDate` is an explicit optional per-run override, defaulting to `issueDate + 15 days` (`DEFAULT_DUE_DAYS` in `bill-run.util.ts`) when omitted. Raising for Srijan to decide whether a real per-tenant setting should replace the constant before Checkpoint B/C, rather than inventing one unilaterally.

**`academicYearId` is an explicit required field on `CreateBillRunDto`**, not inferred from an `is_current` lookup. Spec §5's endpoint bullet ("scope + bsYear + bsMonth") doesn't enumerate every DTO field — matches `FeePreviewQueryDto`'s own explicit-param convention (BILL-2), and other phases' DTOs have consistently been richer than their one-line spec bullet.

**`idempotency_key` is a partial unique index (`WHERE deleted_at IS NULL`), not the spec DDL comment's bare `TEXT UNIQUE`.** A bare unique constraint would permanently block re-drafting a period once its run is voided — §3 says voiding a DRAFT run leaves "nothing to unwind," which only makes sense if the period becomes draftable again. Same partial-unique convention as `uq_sfsa_one_active_per_student_year` (0020_bill_assignment.sql).

**`FAILED` is used for any non-`NotFoundException` error during draft resolution, not only during posting.** The outcome enum's CHECK constraint allows it generically (spec's outcome list isn't scoped to Checkpoint B), and this codebase's established convention (bulk-assign, the old bulk-invoice loop) never aborts a whole batch over one student's error — a single unexpected `FeePreviewService` failure marks that line `FAILED` and the run continues.

**Run-level totals (`bill_runs.total_*`) are computed with one SQL `SUM()` aggregate over `bill_run_lines` after all lines are inserted, not a `Money` accumulator in the per-student loop** — per R1 ("aggregation happens in SQL"), since a whole-school run could be thousands of rows.

**The existing `no-float-coercion.spec.ts` guard caught a real violation during this checkpoint**, working exactly as designed: `bill-run.entity.ts`'s first draft used a local `parseFloat`-based `toNum` helper for its response-DTO mappers. Fixed by importing `toMoney(...).toNumber()` from `finance.entity.ts` instead (the same boundary conversion every other mapper in this module uses) — not a spec deviation, just recorded here since it's the guard test doing its job on brand-new code.

**Live proof (`demo` tenant, Grade 9 — the only class in `demo` with active students, 15 of them):** no fee-structure catalog data existed for Grade 9 at all going in, so a fresh `fee_head` + `bill_fee_structure` (+ one item) + one student assignment (Aarav Shrestha only) were created via the real HTTP endpoints to exercise both outcome paths in one run. `POST /finance/bill/runs` (scope CLASS, bsYear 2082, bsMonth 3 — Ashadh, matching the assignment's `effective_from`) returned `totalStudents:15, outcomeSummary:{DRAFT:1, SKIPPED_NO_ASSIGNMENT:14}, totalGross:3000, totalNet:3000`; a re-POST of the identical period+scope correctly 409'd (`CONFLICT_DUPLICATE`) rather than double-billing. Raw `SELECT`s confirmed: `bill_runs`/`bill_run_lines` rows exist with the exact outcome/amount breakdown; `bill_invoices` count unchanged at 0; `student_ledger_entries` count unchanged at 5 (pre-existing BILL-3 proof rows, untouched). All crafted rows (bill run — cascades to its lines, assignment, fee structure — cascades to its item, fee head) deleted with `COUNT(*)` read-backs afterward; the owner password shim used to obtain a token was restored and 401-proven.

**858 api tests passing (106 suites; +20 this checkpoint: 8 in `bill-run.util.spec.ts`, 12 in `bill-run.service.spec.ts`), `tsc -p tsconfig.build.json --noEmit` clean.**

**Not built this checkpoint (Checkpoints B/C, per explicit instruction):** posting, `PATCH .../exclude`, `POST .../regenerate`, `DELETE .../:id` (void), `GET /finance/bill/invoices*`, sequence numbering, ledger writes, tax snapshot, proration.

## BILL-3 (Phase 4) — Complete, Checkpoint 4, the acceptance bar for the whole spec

**Tables** (`0021_bill_ledger.sql`, canary demo → all 8 tenants): `student_ledger_entries` (append-only — no `updated_at`, no `deleted_at`, the three CHECK constraints verbatim from spec) and `student_account_balances` (one row per student, lifetime running balance — `student_id` is the PK, not composite with `academic_year_id`, exactly as spec's literal DDL). **First trigger/function in this migration system** — `enforce_ledger_immutability()` + `trg_ledger_immutable`, `BEFORE UPDATE OR DELETE`, unconditional `RAISE EXCEPTION` reporting `TG_OP` and the blocked row's id. Both proven live at Checkpoint 4 (raw output below).

**BUGS-5 — opening-balance import is JSON-only, not "CSV or JSON".** Spec §7 says the endpoint "accepts CSV or JSON". Built the JSON-array path only (`OpeningBalanceImportDto.rows`); no CSV parser. A CSV upload would just normalize to this same row shape before doing anything else — the parsing step itself wasn't worth building for this proof, and every other requirement (dry-run preview, per-row status, explicit confirm) is fully exercised by the JSON path. Flagging as scope, not silently narrowing without a note.

**BUGS-6 — opening-balances import split into two explicit routes, not one endpoint toggled by a flag.** Spec §7 writes it as one path: "`POST /finance/ledger/opening-balances` (dry-run + confirm)". Built `POST .../opening-balances/preview` and `POST .../opening-balances/confirm` instead — this mirrors the codebase's own actual existing dry-run/confirm precedent (`students/import`: `POST .../preview` + `POST .../commit`), which the spec's own text credits as the model to follow ("Follows the E.164 backfill precedent from REG-1" — that backfill itself was a one-shot SQL migration with no HTTP dry-run step at all; the real precedent in this codebase is the student-import preview/commit pair). Two explicit routes also means a single boolean flag is never the only thing standing between "just previewing" and a real ledger-affecting commit.

**Live bug found and fixed during Checkpoint 4 proofing, before this commit:** the advisory lock call bound the namespace constant as a parameter — `pg_advisory_xact_lock($1, hashtext($2))` — which 500'd on the very first real opening-balance confirm: `ERROR: function pg_advisory_xact_lock(bigint, integer) does not exist`. The driver defaults a bound JS number to `bigint`; Postgres has no `(bigint, integer)` overload, only `(bigint)` or `(int, int)`. Fixed by inlining the namespace as a literal instead of binding it — the exact pattern `tenant-migration.service.ts`'s own (already-working) advisory lock call already uses, which is why that one never hit this. Re-proven live immediately after the fix (see the opening-balance confirm below).

**Adjustment/reversal narration.** The table has one `narration TEXT` column; the adjustment endpoint requires both `narration` and a separate `reason` (spec's explicit wording). Stored combined as `"[reason] narration"` — a formatting choice, not a structural one, trivially changeable later.

**Not separately live-probed: OWNER_ONLY vs. ACCOUNTANT on adjustments/reverse.** Both routes use the exact same `@Roles(...OWNER_ONLY)` decorator and `RolesGuard` already proven correct (and unit-tested) everywhere else in this module — judged lower marginal value than a fourth live password shim, given the guard mechanism itself isn't new code this phase touches. The cross-family PARENT probe (invariant 8) and the trigger/concurrency probes, which *are* new Phase-4-specific mechanics, got the live-proof budget instead.

**A structural difference from every prior phase's cleanup discipline, worth stating plainly:** `student_ledger_entries` rows created during this Checkpoint 4 proof **cannot be deleted** — that's the whole point of the trigger. Unlike Phases 2–3's "create fresh fixtures, delete with a read-back" pattern, the opening-balance/adjustment/reversal rows posted against the demo tenant's "Chameli Tamang" (chosen specifically for having zero prior invoices/payments, so the proof entries are self-contained and don't mix into any real financial history) are now a permanent part of that tenant's ledger, clearly narrated `[BILL-3 Checkpoint 4 proof]`/`BILL-3 Checkpoint 4 proof —` for anyone who finds them later. ## INC-2 / FIX-QUERY-DTO — Pre-existing bug found live-proofing Phase 2: query DTOs silently ignore filters/pagination over real HTTP (2026-07-25, Phase 2)

**Backlog item `FIX-QUERY-DTO`, for Srijan to prioritize separately — not folded into billing work.** Scope when picked up: audit every query DTO across the codebase (not just finance) for the same undecorated-properties-get-stripped-by-whitelist pattern, decide per-endpoint whether it's cosmetic (web app never sends `search`/custom `page`/`limit` anyway) or a live functional gap (an admin's searches/pagination are silently ignored), and fix the ones that matter using the already-correct `list-students-query.dto.ts` pattern as the template.

**Not a BILL-SPEC deviation — a significant pre-existing bug in the existing finance module (and likely well beyond it), found only because Phase 2's own new endpoints needed a real HTTP proof.**

**What's broken:** `main.ts` sets a global `ValidationPipe({ whitelist: true, transform: true })`. `whitelist: true` strips any request property with **zero class-validator decorators** before it reaches the controller — this is standard, documented NestJS behavior, not a NestJS bug. The *existing* finance query DTOs (`FeeCategoryQueryDto`, `FeeStructureQueryDto`, `InvoiceQueryDto`, `PaymentQueryDto` — all pre-Phase-2) declare `page?: number; limit?: number; search?: string; isActive?: boolean;` with **no decorators at all**. Over real HTTP this means `?search=`, `?page=`, and `?limit=` are silently discarded before the service ever sees them — confirmed live: `GET /finance/fee-categories?search=xyz-should-not-match-zzz` returns the one unrelated existing row anyway, and `?page=1&limit=1` comes back with `meta.limit: 20` (the default), not `1`. **Every list endpoint built on this pattern is unfilterable and unpaginatable from outside the process** — an admin "searching" fee categories/structures/invoices/payments by name today is silently getting the unfiltered first page every time.

**Why nobody caught it:** every existing unit test for these services calls `service.findAll(query)` directly with a hand-built plain object, bypassing `ValidationPipe` entirely — the whitelist-stripping only happens on the real HTTP path, which none of these tests exercise. I only found it because BILL-SPEC's proof standard (§8) requires exercising new endpoints over real HTTP, and my first live search-filter probe against my *own* new `/finance/fee-heads` endpoint came back unfiltered.

**Confirms this is fixable and the correct pattern already exists in this codebase:** `apps/api/src/modules/student/dto/list-students-query.dto.ts` does it right — `@IsOptional() @Type(() => Number) @IsInt() @Min(1) page?: number;` etc. Whichever module wrote that one knew the gotcha; whoever wrote the finance query DTOs didn't hit it (or didn't have live-HTTP proof to catch it).

**What I did:** fixed only my own six new Phase 2 query DTOs (`FeeHeadQueryDto`, `DiscountReasonQueryDto`, `TransportRouteQueryDto`, `TaxRateQueryDto`, `LateFeeRuleQueryDto`, `BillFeeStructureQueryDto`) with proper decorators (`@Type(() => Number) @IsInt()` for page/limit, `@Transform(({value}) => value === 'true') @IsBoolean()` for boolean flags — plain `@IsBoolean()` alone rejects the query-string `"true"`/`"false"`, and `@Type(() => Boolean)` alone is a trap since `Boolean("false")` is `true`). Live-verified after the fix: search now correctly returns zero for a non-matching term and the right row for a real substring match; `?limit=1` now actually caps `meta.limit` at 1.

**Deliberately did NOT touch:** the four pre-existing finance query DTOs, or any query DTO in any other module. Fixing those is a real, valuable, but *separate* piece of work — auditing which of them matter (some list endpoints may only ever be called by the web app with default pagination and no search, making this cosmetic; others may be actively broken for real users right now) is its own scoped task, not something to fold into a billing-catalog migration unilaterally. Flagging for Srijan's prioritization, not fixing pre-emptively.
